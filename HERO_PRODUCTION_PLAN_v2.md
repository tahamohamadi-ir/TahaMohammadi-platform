**Project:** Taha Mohammadi research portfolio  
**Team:** One developer, one Blender workflow, AI-assisted tools  
**Date:** 2026-09-14  
**Deliverable:** Execution plan; artwork and implementation are next steps.

This plan replaces the production requirements in [HERO_VISUAL_SPEC_v1.md](HERO_VISUAL_SPEC_v1.md). ## 0. Decision update — 2026-09-15 (supersedes §7's motion rule for Home)

The owner approved the Stage 3 → Stage 4 architecture and it replaces two rules this document set earlier. Historical intent is kept below on purpose; this section is the current authority.

1. **A scroll-driven image sequence on Home is now approved** on both desktop and mobile. §7's earlier sentence — *"No idle loop, scroll scrubbing, autoplay video, image sequence, particle motion"* — recorded the first-release intent (a single polished still) and is **superseded for Home** by the four authored Stage 3 states (`Design-Assets/hero-v2/source/hero-v2-stage3.blend`, renders under `renders/stage3/`, validation 22/22 in `validation/hero-v2-stage3-validation.json`, owner-approved 2026-09-15).
2. **Mobile is no longer automatically static.** §7's *"Mobile, coarse pointers, and reduced motion use a static image"* is superseded: the mobile composition is an independently authored camera and scrubs too. Reduced motion still resolves to **one static representative frame**, and any genuine capability fallback must be documented separately rather than treating all mobile devices as static.
3. **What still holds, unchanged:** scroll progress is the only motion driver; no idle loop, no autoplay, no video, no continuous WebGL rendering on Home, no CSS rotation or scale trickery to fake depth; text, labels and controls stay stationary and real HTML; the deeper interactive experience stays on About.
4. **Home no longer hosts the interactive WebGL graph.** The image hero replaces it, per this document's own "Do not duplicate an interactive graph explorer on Home": Home keeps lightweight renders plus real HTML copy, and drag/rotate/zoom/node selection remains About-only.

## 1. Final visual goal

**A quiet, cinematic research constellation that looks premium before anything moves.**

Place four tactile, organic forms beside the introduction: a central identity sphere with three companions. Soft studio light, subtle material differences, and deliberate spacing provide depth. The result should feel like a carefully photographed design object within an editorial website.

| Form | Meaning | Shape direction |
|---|---|---|
| Core | Taha Mohammadi's organizing identity | Soft mineral sphere, one recessed seam, restrained warm-metal detail |
| Human-Centered AI | Research axis | Rounded shell with one generous opening around an inset form |
| AI for Health & Human Behavior | Research axis | Smooth sphere with two shallow contours following its volume |
| Wearable / Edge Intelligence | Research axis | Compact sphere with three broad, rounded segments |

These axes come from the existing [product direction](Docs/05-delivery/concept-alignment-v2/PRODUCT-SPEC.md). Shapes are visual metaphors, not diagrams of research findings. The core is decorative; sphere size and position do not encode importance or achievement. Existing RU-3 project-domain models must not be relabeled as these axes.

The name, introduction, and useful links remain the reading priority. Home introduces the research identity; About is the place for exploration, node selection, and richer context. Do not duplicate an interactive graph explorer on Home.

Keep the Home free of portal architecture, neon fog, star fields, anatomical imagery, dashboards, and floating interface panels. Premium quality comes from silhouette, light, typography, and empty space.

## 2. Asset strategy

**Ship pre-rendered stills first.** Use one Blender scene, two camera compositions, and two theme presets. The page displays one responsive image at a time. A small optional whole-image movement can add polish without additional renders.

| Required | Quantity | Purpose |
|---|---:|---|
| Editable Blender file | 1 | All four forms, both cameras, and both theme presets |
| Final transparent PNG renders | 4 | Desktop Light/Dark and mobile Light/Dark |
| WebP derivatives | 6 | Two desktop widths per theme; one mobile width per theme |

There is no mandatory GLB, texture-baking package, video, sprite sheet, render sequence, EXR, depth pass, object mask, or multilayer compositing. Tablet reuses the desktop composition.

Keep the files together in one dedicated hero asset folder, with `source` and `web` subfolders. Use simple names such as `hero-v2.blend`, `hero-desktop-light.png`, `hero-desktop-light-800.webp`, and `hero-mobile-dark-800.webp`. Version control and the existing media promotion process are enough; do not build a separate asset-management system. A short note in the existing task handoff can record chosen files, dimensions, bytes, and remaining work. Do not overwrite existing portal or RU-3 assets.

Use AI assistance for Blender operations, variations within this direction, export chores, compression, and browser checks. Keep the editable Blender scene as the source of truth. AI should not invent labels, translations, research relationships, or owner facts.

## 3. Blender workflow

### Model the silhouette first

Start from sphere primitives. Give each companion a diameter of 1 unit and the core 1.45 units. Keep companions equal in rank. Add only the opening, contour, or segmentation that makes each form recognizable. Broad organic deformation should stay within roughly 2–4% of diameter. Use rounded bevels and smooth shading; avoid tiny mechanical details that disappear on a phone.

Arrange the core slightly forward with companions above-left, right, and below-left. Preserve visible gaps between silhouettes. A connected scientific network is not baked into this image: use at most one faint, incomplete orbital arc as decoration, without endpoints or arrowheads. Real relationships belong to the data-driven experience on About.

### Use four simple material roles

| Role | Metallic | Roughness | Appearance |
|---|---:|---:|---|
| Shell | 0 | 0.34–0.44 | Satin mineral ceramic |
| Inset | 0 | 0.48–0.60 | Matte inner surface |
| Accent | 0.75–0.90 | 0.28–0.38 | Small brushed-metal detail |
| Brand detail | 0 | 0.28–0.38 | Restrained teal surface |

Use a dielectric IOR around 1.45 as a starting point. Keep metal below approximately 5% of visible object area. No transparent glass shells or emission-dependent appearance. Geometry and broad reflections should carry the quality.

Procedural texture is optional and subtle. Skip image textures and UV work for the still-image release unless a visible close-up defect requires them. At normal page size, the finish should read as smooth and tactile, not noisy or weathered.

| Palette role | Light | Dark |
|---|---|---|
| Page canvas | `#f7f8f5` | `#071225` |
| Reading ink | `#182328` | `#f7f3ea` |
| Brand | `#087c73` | `#16b8a6` |
| Signature | `#a77b28` | `#c89b3c` |

Use warm mineral shells in Light and navy shells with readable warm edges in Dark. Change the actual material/light preset; do not invert the Light render. Typography uses existing Newsreader/Inter for English and Estedad/Vazirmatn for Persian.

### Light it like a small studio object

Use three broad area lights: key above and in front from the left, soft fill from the right, and a restrained rear rim. Start with relative strengths of **1 : 0.3 : 0.35** in Light and **1 : 0.18 : 0.55** in Dark. Adjust exposure until the forms read clearly; do not chase exact wattage.

Keep the key near-neutral and the rim slightly warm. Render with transparent film and no floor. Self-shadowing inside seams and openings is enough. Avoid bloom, volumetrics, lens flare, and a background gradient baked into the image.

### Set only two cameras

- **Desktop/tablet:** near-frontal perspective, approximately 70mm on a 36mm sensor. Fit the four forms into an open diamond with at least 8% clear space at the image edges.
- **Mobile:** orthographic or very long-lens view, with a tighter diamond and shallower depth. Reposition companions to keep all four visible at 320px page width.

Disable depth of field initially. Add only a slight amount if it visibly improves the desktop image without softening a companion. Use Cycles, denoising, and approximately 128 samples for final renders; increase only if the actual output still shows noise or damaged seams. Use low-resolution previews during iteration.

## 4. Required renders only

Produce **four final views**, each in one settled pose:

| Render | Source size | Web exports |
|---|---|---|
| Desktop Light | 1600 × 1400 PNG | 800px and 1600px wide WebP |
| Desktop Dark | 1600 × 1400 PNG | 800px and 1600px wide WebP |
| Mobile Light | 800 × 800 PNG | 800px wide WebP |
| Mobile Dark | 800 × 800 PNG | 800px wide WebP |

Export display-ready sRGB with transparency. Check the compressed results over the exact Light and Dark page colors, especially around thin edges and openings. Keep the uncompressed PNGs as editable-source outputs; serve the WebP files.

No separate tablet, hover, selected-node, extreme-angle, isolated-node, or turntable renders are required. The six WebP files are resized/encoded derivatives of four renders, not six new render jobs. Add another view only when an actual layout problem cannot be solved with these compositions.

Review each final at normal desktop size and at approximately 320px scene width. Once the still looks right inside the real hero, stop look development and integrate it.

## 5. Web implementation strategy

### First release: responsive image and HTML

Use the existing Astro page and responsive image handling. Keep the name, introduction, approved research-axis text, and CTAs as real HTML. The artwork is decorative alongside that text and receives an empty alternative description to avoid duplication. It does not pretend to be a live published graph.

Choose the appropriate desktop/mobile source and theme before requesting the image. Reserve its layout space from the first render. Do not initially fetch every theme and resolution. Keep the image visible without JavaScript; a saved theme preference should be resolved through the existing theme mechanism before image selection where possible.

Keep labels in a stable HTML group beside or below the art, using exact approved localized content. Do not build invisible image hotspots or overlay a fake interactive node network. Use an ordinary link to the existing localized About destination for deeper exploration; confirm the actual route and copy before integration. Do not invent a new endpoint or route.

No Home graph-detail panel, orbit controls, zoom toolbar, or model loader is needed for this release. Preserve useful existing information and navigation when simplifying the hero; move deeper exploration through the existing About experience rather than silently deleting content. If source content is missing, show the appropriate content state. The decorative four-form image is not proof that four published graph nodes exist.

### Optional later enhancement: a small 3D scene

Only consider this after the image-first Home is integrated. A live-lighting comparison must show a clear improvement at normal page size before adding the cost. Static delivery is a finished outcome, not an incomplete fallback.

If selected, reuse the Blender forms in one simplified GLB with basic materials. Keep the same framing and HTML, no new graph behavior. Reuse the existing renderer infrastructure; do not introduce a second framework or custom shaders. Load after useful content, retain the poster on failure, and render only while the view changes. Skip it on mobile, under reduced motion, and when the device cannot meet budget. Model export and a focused fallback check belong to that later change, not today's render list.

## 6. Responsive behavior

| Viewport | Layout | Art behavior |
|---|---|---|
| Desktop, ≥1024px | Copy at inline-start, artwork at inline-end; approximately 5/7 columns; max content width 1280px | Use desktop image, contained in a scene area around 520–620px high |
| Tablet, 768–1023px | Stack copy/actions, artwork, then supporting links; 24px gutters | Reuse desktop image; scene around 380–460px high |
| Mobile, 320–767px | Single column; 16px gutters; copy/actions before art | Use mobile image; scene around 280–360px high |

Use containment, not a destructive cover crop. It is fine to have some clear space around the image. Keep every primary sphere visible, with at least roughly 12px between silhouettes at the narrowest size. Reduce the art's displayed scale before sacrificing text or touch targets.

English places copy left and art right; Persian reverses the layout columns without mirroring the artwork. On stacked layouts, both languages retain the same reading order. All body text stays at least 16px and interactive targets at least 44 × 44px. Do not fit the entire hero into one fixed viewport height. At 200% zoom, allow natural wrapping and growth.

## 7. Animation strategy

> **Superseded for Home by §0 (2026-09-15).** The still below remains the correct description of the first-release intent and still governs the optional pointer response; Home now also ships the approved four-state scroll sequence, on mobile as well as desktop.

**Default: a polished still. Optional: one restrained motion behavior.**

After the still is satisfactory, the developer may add a fine-pointer response on desktop: translate the entire image by at most **4px** and tilt it by at most **1°**, easing back over about **200ms**. Treat this as a small image-plane movement; it cannot create true changing reflections or independent depth. If it reads like a floating card, remove the tilt and retain translation only—or keep the still.

Move the whole artwork as one element. Do not separate nodes into render layers or generate additional frames. Text, labels, and controls remain stationary. Ensure the full movement envelope fits the art slot.

Mobile, coarse pointers, and reduced motion use a static image. No idle loop, scroll scrubbing, autoplay video, image sequence, particle motion, or entrance that hides useful content. Use a small local controller or existing scoped motion capability; do not load an animation library solely for this effect. Work stops when the pointer settles, leaves, or the hero is offscreen.

Deeper movement and graph interaction belong to About's separate experience and are outside this Home production task.

## 8. Performance budget

These are implementation targets, not measured results. Optimize the image first; do not trade away visible material quality merely to minimize a byte count.

| First-release item | Budget |
|---|---|
| Mobile hero image | Target ≤140 KiB; ceiling 180 KiB |
| Tablet-selected image | Ceiling 200 KiB |
| Desktop hero image | Target ≤240 KiB; ceiling 300 KiB |
| Initial hero image requests | One selected theme, composition, and resolution |
| Added Home motion JavaScript | 0 by default; ≤10 KiB gzip if added, including dependencies |
| Home renderer/model downloads | Zero for the image-first release |
| Layout stability | Reserve image dimensions; no image-induced layout shift |
| Idle animation | Zero continuous work |
| Whole-page targets | LCP ≤2.5s, CLS ≤0.1, INP ≤200ms; preserve existing project checks |

If an export is too large, remove invisible microtexture, tune compression, and then reduce resolution. Inspect the actual compressed result for banding and edge artifacts. Use AVIF only if a quick comparison gives a useful saving at equal visible quality; it is not a required second asset pipeline. Do not lazy-load the hero image if it is the likely largest above-the-fold element; avoid preloading candidates that the browser will not use.

For a later desktop 3D enhancement, keep **GLB ≤350 KiB, model geometry ≤15,000 triangles, draw calls ≤30, one canvas, DPR ≤1.5, and drawing buffer ≤1.5 million pixels**. No separate texture/environment downloads are planned. Combined fetched poster/model assets must stay ≤700 KiB; renderer, loader, motion, and decoder code combined must remain within the existing ≤300 KiB gzip route ceiling. Target interaction frames within 16.7ms and stop rendering when idle. If this does not fit, retain the still.

For this small team, one cold-load mobile browser check and a desktop comparison are enough to guide optimization. Use existing project tests for regressions; do not create a separate hero analytics or performance reporting system. Local checks guide release decisions; actual deployed field performance remains a separate measurement.

## 9. Step-by-step execution checklist

1. **Confirm content and placement.** Use the existing identity, research-axis copy, fonts, and theme tokens. Confirm the existing About link. Preserve v1 as history; use this plan for Home production.
2. **Block the four forms in Blender.** Work in one dedicated file. Check the large-to-small hierarchy and distinguishable silhouettes with a simple gray preview. Do not detail surfaces yet.
3. **Compose desktop and mobile.** Set the two cameras. Test a small preview inside the actual hero layout; fix spacing before polishing materials.
4. **Finish materials and lighting.** Tune Light and Dark from the same scene. Concentrate on broad highlights, warm edges, and clear openings. Use AI assistance for repetitive operations and bounded variations.
5. **Render the four stills.** Export the four PNGs in §4. Inspect at page size. Re-render only the views with visible problems.
6. **Create the six web derivatives.** Compress, inspect alpha edges and gradients, and record file sizes in the existing handoff. Use the existing asset promotion mechanism once the selected files are reviewed.
7. **Integrate the static Home hero.** Add responsive/theme selection, reserved sizing, HTML copy, and the About link. Ensure only the chosen image downloads initially. Keep the no-JavaScript page complete.
8. **Decide whether motion earns its cost.** Try the bounded whole-image response only after the still works. Remove it if it distracts or exposes the flat image plane. Do not begin the optional WebGL upgrade automatically.
9. **Run one focused final check.** Inspect desktop, tablet, and phone layouts in both themes; check English and Persian wrapping, 320px overflow, keyboard links, reduced motion, 200% zoom, and a cold mobile load. Reuse existing repository checks appropriate to the frontend change. Fix observed problems rather than generating a large screenshot matrix.
10. **Close the handoff.** Save the Blender source, selected web assets, and a short note of what shipped and what remains. Update the existing project status. Complete the normal owner visual review and release process without creating additional approval layers.

**Finished outcome:** a premium, responsive Home hero built from four final renders, readable HTML, and at most a small optional motion effect. The deeper interactive research experience remains on About. No VFX production pipeline is required.
